## 📌 1. О проекте: Назначение и Архитектурный стек

**JLPT Dokkai Master** — интерактивное веб-приложение для подготовки к экзамену по японскому языку JLPT (уровни N5–N1), сфокусированное на секции понимания прочитанного (読解, Dokkai).

### 🛠️ Технологический стек:
* **Бэкенд:** Python 3.11+, FastAPI, Pydantic v2, SQLAlchemy ORM (SQLite в локальной разработке / PostgreSQL на хостинге Render).
* **Фронтенд:** Vanilla JavaScript ES6+ (модульная архитектура, Web Components / Template Strings), CSS3 (BEM-подобный, модули без CSS-фреймворков), HTML5.
* **PWA & Офлайн:** Service Worker (`static/sw.js`) со строгой политикой `network-first` для статики и полной изоляцией API.
* **Хранилище:** IndexedDB (`DokkaiStorage`, БД `dokkai_master_db`), LocalStorage (настройки, резервный кэш), Firebase Firestore (облачная синхронизация `users/{uid}/sync/state`).
* **Аутентификация:** Firebase Auth (Google Sign-In с fallback на redirect, анонимный гостевой вход).
* **Лингвистический движок:** Собственный токенизатор и парсер фуриганы (`<ruby>漢字<rt>かんじ</rt></ruby>`), интерактивный словарь в стиле Yomichan, озвучка японского языка через Web Speech API (`ja-JP`).
* **QA и Верификация:** Playwright Test Suite (100+ тестов, поддержка профилей Desktop HD и Mobile iPhone 390), библиотека axe-core (доступность WCAG AA), Pillow (пиксельный diff с допуском 0), вспомогательные CJS-скрипты сравнения DOM и сетевых запросов.

### 👥 Мультиагентная система проекта:
В репозитории сконфигурированы два специализированных агента (см. `AGENTS.md` и `.agents/agents/`):
1. **`@jlpt-expert`** — лингвист-методолог JLPT (N5–N1). Отвечает за проверку разметки фуриганы, точность дистракторов (почему 3 варианта неверны, а 1 верен), разметку доказательств (`evidence_span_id`) и адаптацию японских текстов.
2. **`@senior-dev`** — Senior Software Engineer. Отвечает за архитектуру FastAPI, безопасность Anti-Cheat, null-safety, клиентскую логику, тесты и оптимизацию.

## 📜 2. Главные правила и инварианты проекта (ОБЯЗАТЕЛЬНЫ К ИСПОЛНЕНИЮ)

1. **Режим подитераций и остановка:** Каждая подитерация выполняется строго по очереди. Запрещено переходить к следующей подитерации без явного подтверждения пользователя («ок») на отчёт по предыдущей.
2. **Нулевая регрессия в Частях I и II (100% паритет с веткой `main`):**
   * Поведение, внешний вид, верстка, доступность, публичные URL, контракты API, формат хранилища (IndexedDB/localStorage) и структура Firestore (`users/{uid}/sync/state`) **НЕ МЕНЯЮТСЯ**.
   * Пиксельное сравнение скриншотов с веткой `main` (`compare_screenshots.cjs` + `pixel_diff.py`): **допуск 0 пикселей (0.0000%)**.
   * Сравнение вычисленных стилей (`compare_computed_styles.cjs`): **0 расхождений по всем 9 экранам**.
   * Сравнение сетевых запросов (`compare_network_flow.cjs`): **100% bit-for-bit совпадение по всем 28 эндпоинтам**.
3. **Протокол Anti-Cheat:** До отправки задания на проверку через `/api/stream/complete` сервер **никогда** не отдаёт клиенту `is_correct`, `explanation`, `trap_type` или `evidence_span_id`. Никаких утечек ответов в DOM, state, storage или сетевом трафике!
4. **Достоверность отчётов и `git log`:**
   * Запрещено выдумывать хеши или сообщения коммитов. Хеши и сообщения берутся **только** из реального вывода `git log --oneline -15` в текущем сеансе.
   * Запрещено заявлять, что тесты прошли, без их фактического выполнения.
5. **Баги и намеренные отличия:** Ничего не исправлять «молча». Любые найденные дефекты фиксируются в `docs/INTENTIONAL_DIFFERENCES.md` с указанием причины и показываются пользователю.
6. **Лингвистическая точность:** Чтения и фуригана генерируются токенизатором, а не выдумываются нейросетью. Источники и тексты JLPT не фальсифицируются.
7. **Безопасность окружения:** Секреты — только в `.env` (не коммитить). Браузерный агент работает только с `localhost`. Деструктивные команды (`rm -rf`, `DROP TABLE`) без явного разрешения запрещены.

* **Диагностика C (Мобильный интерфейс):** Проведен автоаудит на 6 разрешениях в DPR 1, 2 и 3:
  * *C1 («Неровности»):* диагностированы субпиксельные артефакты плашки отправки ответов на экранах с высоким DPR.

Разработан дизайн безопасного перемешивания через криптографический HMAC (`SHUFFLE_SECRET`), с сохранением стабильности попытки и исключением порядок-зависимых вопросов (числа, даты, «все вышеперечисленные»).
